# r0-mobile: reconhecimento de lembretes/alarmes no app Ben (somente leitura)

M = packages/infra/mobile/ben. Premissa: "lembrete/alarme" do pedido = entidade `Reminder` (kind `alarm`/`goal`/`conditional`).

## 1. Como lembretes funcionam hoje no mobile
- Horário nasce no backend: o agente cria o `Reminder` em `persist-captures` (packages/domain/chat/.../captures/persist-captures.ts:157-161) e `computeNextFireAt` (packages/domain/chat/src/application/utils/reminders.ts:207) calcula `nextFireAt`. O mobile só lê (`Reminder.firesAt`, `nextFireAt`, `snoozedUntil`: M/src/api/models/reminder.ts:34-43).
- Notificação é LOCAL agendada, não push do servidor: `scheduleNotificationAsync` com trigger DATE em M/src/services/notifications-service.ts:122-134 (identifier = reminder.id, data `{reminderId, nextFireAt}`, `channelId: 'alarmes'`). `syncReminderNotifications` (:150-172) reagenda os ativos e cancela o resto; é chamado por `useAlarmScheduler` a cada mudança da lista (M/src/layout/hooks/use-alarm-scheduler.ts:45-50).
- Canais Android (notifications-service.ts:7-27): `alarmes` ("Reminders", `AndroidImportance.HIGH`), `resumos` ("Daily summary", DEFAULT). Nenhum `sound` customizado, `bypassDnd`, `vibrationPattern` nem `audioAttributes` definido (usa som padrão de notificação). Canal legado `default` é apagado (:54). Handler em primeiro plano: banner + som (:32-39).
- Dentro do app (aberto): `useAlarmScheduler` checa a cada 15 s (`CHECK_INTERVAL_MS`, use-alarm-scheduler.ts:11,40) lembretes com `nextFireAt` vencido e enfileira no `alarm-store` (M/src/layout/stores/alarm-store.ts:102-126, dedupe `id:firedAt`). `AlarmPopupOverlay` (M/src/layout/components/alarm-popup/alarm-popup-overlay.tsx:264-282) abre isso num `Modal` transparente tipo bottom sheet (`SettingsSheetOverlay`, M/src/layout/components/menu-settings/settings-sheet-overlay.tsx:5-50), montado no layout autenticado (M/app/(protected)/_layout.tsx:28). NÃO é tela cheia, não toca som próprio, não acorda a tela.
- Conteúdo do popup `alarm`: rótulo, título, "evento às HH:MM", botões OK / Snooze / Complete (M/src/layout/components/alarm-popup/alarm-popup-alarm.tsx:27-68). Snooze abre `alarm-popup-snooze.tsx` com opções de `GET /reminders/:id/snooze-options` (10 min, 30 min, 1 h, 2 h, amanhã de manhã; M/src/api/models/reminder.ts:21-27). OK/soneca chamam `requestAcknowledgeReminder` (overlay :183-189), concluir chama `requestUpdateReminder({status:'done'})` (:190-191). `goal` e `conditional` têm popups próprios (overlay :236-252).
- Toque na notificação: `subscribeToNotificationTaps` (notifications-service.ts:224-238) entrega `{reminderId, nextFireAt}`; não navega para rota alguma: o `useAlarmScheduler` busca `requestActiveReminders` e enfileira o alarme no store (use-alarm-scheduler.ts:52-71), e o popup aparece sobre a tela atual. Notificação sem `reminderId`/`nextFireAt` é ignorada (:213-215).
- Cold start: `getLastNotificationResponse()` + `clearLastNotificationResponse()` no subscribe (:231-235), dedupe por `identifier:date` (:216-220). Só roda depois do login (`if (!userId) return`, use-alarm-scheduler.ts:53-55), dentro do layout autenticado.
- Push remoto (task notificacoes-correcoes, docs em .claude/tasks/2026-10-30_notificacoes-correcoes/{plan,recon,review-r1,checklist-externo}.md): só há push de TESTE (`POST /push-devices/test`, packages/infra/server-ben/src/app.ts:100-101; copy fixa em routes/push-devices/send-test-push.ts). O plano diz explicitamente "sem agendador, sem push de lembrete" (plan.md, premissas). Lembretes não passam pelo servidor para disparar.
- Plugins de notificação: `expo-notifications` com `icon` e `color` apenas, sem `sounds` (M/app.config.ts:47-53). O plugin suporta `sounds` (node_modules/expo-notifications/plugin/build/withNotificationsAndroid.js:68) mas não é usado.
- Resumo diário: notificação local DAILY no canal `resumos` (notifications-service.ts:174-195).
- Web: serviço inteiro é no-op (M/src/services/notifications-service.web.ts); então no :8081 só funciona o popup in-app (15 s de polling), nada de notificação.
